## Role in this project

The forward-private, verifiable DSSE baseline with efficient **conjunctive**
query support — the closest baseline to the proposed scheme's `q = 5`
multi-keyword workload.

Like Scheme 30, it verifies with a single tag over the whole result set, so it
is the second member of the **aggregate-verification family** in Experiments 4
and 9: a tampered record cannot be named, and the whole batch is rejected.

---

## How the scheme works

```
src/scheme.py   Algorithms 1–4: Setup, Update, Search, Verify
src/index.py    the encrypted database (EDB)
src/state.py    client state
```

The encrypted database is **two hash tables plus a cache**, per the paper's
`EDB = {Ti, Tf}`:

| Structure | Keyed by | Holds |
|---|---|---|
| `Ti` — inverted index | tag | `(data, vt)` |
| `Tf` — forward index | document id | `(data', vt')` |
| cache | version key | previous query results |

- **Setup** (Alg. 1) initialises the client state and the two tables.
- **Update** (Alg. 2) draws a per-document random key for the forward index and
  writes inverted-index entries under PRF-derived tags. Forward privacy comes
  from the puncturable PRF: a punctured key cannot regenerate earlier tags.
- **Search** (Alg. 3) scans the inverted index for the least-frequent keyword,
  counting down through its version chain; for a **conjunctive** query it then
  performs forward-index lookups on the candidates and filters client-side.
  The two paths are distinguished by `token.conjunctive`.
- **Verify** (Alg. 4) checks the returned result set against the accumulated
  verification tags — `accept`/`reject` over the whole set, not per record.

The dual-index design is the point: the inverted index makes the first keyword
cheap, and the forward index turns the remaining conjuncts into direct lookups
rather than further scans.

`H1` and `H2` are SHA-256 truncated to 192 bits, per the paper. They operate on
EDB-level data — tag addresses and payload masks — and are used by no other
scheme, so they live in `index.py` rather than in `Common/`.

## Measurement notes

**Experiment 2's boundary** is the full online path: token generation → server
inverted-index retrieval → forward-index filtering → client final evaluation →
result assembly. Index construction is offline and untimed.

## Implementation notes

- **Experiment 2 is the campaign's memory ceiling.** Its forward index needs
  roughly 52 GB at `N = 10⁶`, which is why the campaign stopped pinning a single
  instance type and now sizes hosts per scheme. The host actually used is
  recorded in each `run_meta.json`.
- The keyword selected for a sweep is drawn **once** before the loop and reused
  at every point. Drawing inside the loop would let query selectivity vary with
  `N` and contaminate the curve.
- Algorithm and line citations throughout `scheme.py` point at
  `References/Ref[35]/`.
