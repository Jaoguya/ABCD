## Role in this project

The verifiable multilevel DSSE baseline, and the broadest of the four — the only
one besides Scheme 35 present in Experiments 4 (both arms) *and* 5.

In Experiment 4 it represents the **aggregate-verification family**: one
digest over the whole result set, so a single tampered record forces the whole
batch to be rejected. That is the behaviour the proposed scheme's per-entry
Merkle verification is measured against.

## How the scheme works

```
src/peony.py        Peony (§V) — forward-private base
src/peony_plus.py   Peony++ (§VI) — the default variant
src/msre.py         Multilevel Symmetric Revocable Encryption (§IV)
src/levels.py       multilevel access policy
src/index.py        encrypted index structures
src/digest.py       on-chain prooflist digests
```

**Peony (§V)** is the forward-private base: keywords index into linked lists of
file identifiers, with deletion written into the index as a `del` entry.

**Peony++ (§VI)** is the default measured variant and changes three things:

1. **Nodes carry MSRE ciphertexts, not plaintext identifiers.** `ListGen`
   computes a tag `t = F_Kt(w, id)` and stores
   `ct = MSRE.Enc(lsk, id, a(id), t)`. The server walks the same linked list but
   must run `MSRE.Dec` to learn an identifier.
2. **Deletion never touches the server.** The owner inserts the tag into its own
   Bloom filters instead of writing a delete flag. That is the Type-II
   backward-privacy mechanism: the server is not asked to *honour* a deletion,
   it is made *unable* to decrypt — and it is why the paper's deletion cost is
   microseconds, with no round trip.
3. **Every `Add` publishes a digest.** `prooflist[pt_wl]` commits to the files
   added at level ≤ `l` in a batch, and `Verify` recomputes it.

**MSRE (§IV)** generalises symmetric revocable encryption from one revocation
filter to one per access level. A file identifier is encrypted `h` times, once
per Bloom position its tag hashes to. Revoking sets those `h` positions and
hands the server a GGM key punctured at every set position: the server can still
derive a leaf key for any zero position, and nothing for a revoked tag.
Correctness error comes only from the Bloom false-positive rate, which the paper
states plainly.

### The verification algebra

This is what makes verification constant-size rather than proportional to the
result set — and what makes tamper localization impossible.

```
prooflist[pt_wl] = H(0, r_wl) XOR (XOR over j added, level<=l  of H(1, C_idj))
proof_del        = (XOR over j deleted of H(1, C_idj)) XOR (XOR over i of H(0, r_i))
```

XOR the prooflist entries across batches, then XOR in `proof_del`: the
`H(0, r_i)` terms cancel pairwise, deleted `H(1, C_id)` terms cancel against
their own additions, and what survives is exactly the XOR over files still
present. Multiset hashing over XOR — order-independent, one 32-byte digest
however many files match.

**Consequence, and what Exp. 4's `granularity` arm records:** at every `t`,
`records_discarded` is the full result-set size (20,000) and
`tampered_localised` is 0. A correct property of the published construction,
reported as a finding rather than corrected.

## Configuration

`crypto.yaml`, `yue_ge` block.

| Key | Value | Provenance |
|---|---|---|
| `access_levels` | 3 | published — level 3 highest |
| `bloom_filter.false_positive_rate` | 1e-4 | published |
| `bloom_filter.num_hashes` | 5 | published, primary |
| `bloom_filter.num_hashes_alt` | 13 | published alternate |
| `deletions_between_searches` | 1000 | the paper's own Table VII point |
| `file_identifier_bytes` | 32 | published |
| `hash` / `digest_hash` | sha256 / keccak256 | keccak for on-chain prooflist entries |
| `symmetric_encryption` | aes-256-gcm | |
| `security_parameter_lambda` | 128 | |
| `update_batches_c` | 4 | |
| `puncturable_prf.output_bits` | 256 | |
| `level_assignment` | `pid_hash` | **benchmark, not published** |

**The one derived quantity.** Bloom array size `b` is not a stored constant; it
is the paper's §VII-B formula `b = -d·ln(p)/(ln 2)²`, computed per
(keyword, level) filter, so it grows with deletion volume. `test_scheme.py`
checks it against the paper's own Table V storage figures.

**Why `level_assignment` is a benchmark decision.** The paper never says how it
assigned access levels to its Wikipedia corpus, and the Synthea corpus carries
no sensitivity attribute — records hold `rid/pid/vid/dom/ts/kw` and nothing
else. The level is derived deterministically from the pseudonymous patient
identifier, which keeps it reproducible across runs and machines without storing
a level map.

## Scheme-specific flags

Beyond the common contract in [skill.md](skill.md) §7:

| Flag | Values | Effect |
|---|---|---|
| `--variant` | `peony_plus` (default), `peony` | which construction is measured |
| `--bloom-hashes` | 5, 13 | overrides `h`; the paper publishes both and declares no default |

Output flag is `--output-dir`; warm-ups are `--warmup`. No `--dataset`.

**`--variant peony` with `--experiment 4` is refused.** Peony (§V) has no
verification algorithm — public verification is introduced by Peony++ (§VI-A).
The runner exits rather than measuring something else and labelling it
verification.

```bash
python3 -m Schemes.yue_ge.src.main --experiment 2 --variant peony
python3 -m Schemes.yue_ge.src.main --experiment 2 --bloom-hashes 13
```

## Implementation notes

- Peony++ is the default because it is the paper's flagship and the only variant
  supporting Experiment 4.
- It entered Experiment 4 because it has a scheme-native `Verify`, and
  Experiment 5 because it has a native incremental `Add` — a new batch is
  appended and nothing is rewritten, which is what Experiment 5 measures.
- Primitives the paper *cites* rather than invents come from `Common/`, the GGM
  puncturable PRF among them. MSRE, the multilevel policy and the prooflist
  algebra are scheme-specific and live here.
