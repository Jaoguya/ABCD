================================================================
 MA-LB-PQ-VDSE — EXPLANATION: SYSTEM MODEL & PROTOCOL PHASES
 (English / Thai)
================================================================


================================================================
 PART 1 — SYSTEM MODEL
 ส่วนที่ 1 — แบบจำลองระบบ
================================================================

[EN] The system model describes WHO takes part in the framework and
WHAT role each of them plays. There are 9 entities.

[TH] แบบจำลองระบบอธิบายว่า "ใคร" มีส่วนร่วมในกรอบการทำงานนี้ และ
"แต่ละฝ่ายทำหน้าที่อะไร" โดยมีผู้เกี่ยวข้องทั้งหมด 9 ประเภท


----------------------------------------------------------------
1. IoMT Devices and Gateways
   อุปกรณ์ IoMT และเกตเวย์
----------------------------------------------------------------
[EN] Wearable sensors, patient monitors, medical imaging equipment,
and devices on smart ambulances constantly generate healthcare data.
Edge gateways collect this data, preprocess it, and send it — already
encrypted — to the cloud/fog infrastructure.

[TH] อุปกรณ์สวมใส่ เครื่องมอนิเตอร์ผู้ป่วย เครื่องมือถ่ายภาพทางการแพทย์
และอุปกรณ์บนรถพยาบาลอัจฉริยะ สร้างข้อมูลสุขภาพอย่างต่อเนื่อง เกตเวย์
ที่ขอบเครือข่ายจะรวบรวมข้อมูลเหล่านี้ ประมวลผลเบื้องต้น แล้วส่งข้อมูล
ที่เข้ารหัสแล้วไปยังโครงสร้างพื้นฐานคลาวด์/ฟ็อก


----------------------------------------------------------------
2. Data Owner (DO)
   เจ้าของข้อมูล (DO)
----------------------------------------------------------------
[EN] A hospital, clinic, laboratory, or healthcare provider. The DO
encrypts IoMT data, builds the searchable index, defines who is
allowed to access it (access policy), signs the encrypted records,
uploads the ciphertext to IPFS, and registers metadata on the
blockchain.

[TH] คือโรงพยาบาล คลินิก ห้องปฏิบัติการ หรือผู้ให้บริการด้านสุขภาพ
เจ้าของข้อมูลจะเข้ารหัสข้อมูล IoMT สร้างดัชนีค้นหา กำหนดว่าใครมีสิทธิ์
เข้าถึงข้อมูลได้บ้าง (นโยบายการเข้าถึง) เซ็นรับรองระเบียนที่เข้ารหัสแล้ว
อัปโหลดข้อมูลเข้ารหัสไปยัง IPFS และลงทะเบียนเมทาดาทาบนบล็อกเชน


----------------------------------------------------------------
3. Data User (DU)
   ผู้ใช้ข้อมูล (DU)
----------------------------------------------------------------
[EN] Authorized physicians, specialists, emergency responders, and
researchers who search for and decrypt records they're allowed to
see. Each user holds attribute-based secret keys issued by one or
more Attribute Authorities.

[TH] แพทย์ ผู้เชี่ยวชาญ หน่วยกู้ภัยฉุกเฉิน และนักวิจัยที่ได้รับอนุญาต
จะเป็นผู้ค้นหาและถอดรหัสข้อมูลที่ตนมีสิทธิ์เข้าถึง ผู้ใช้แต่ละคนถือกุญแจลับ
ตามคุณลักษณะ (attribute) ที่ออกโดยผู้มีอำนาจหนึ่งรายหรือมากกว่า


----------------------------------------------------------------
4. Multi-Authority (MA / AA)
   หลายผู้มีอำนาจ (MA / AA)
----------------------------------------------------------------
[EN] Multiple independent Attribute Authorities — e.g. hospitals,
insurance providers, government agencies — each manage user
attributes within their own domain. Each authority independently
handles user registration, attribute issuance, and revocation. No
single trusted central authority is needed after setup.

[TH] ผู้มีอำนาจด้านคุณลักษณะ (Attribute Authority) หลายรายที่เป็นอิสระ
จากกัน เช่น โรงพยาบาล บริษัทประกัน หน่วยงานรัฐ ต่างจัดการคุณลักษณะ
ของผู้ใช้ในโดเมนของตนเอง แต่ละผู้มีอำนาจดำเนินการลงทะเบียนผู้ใช้ ออก
คุณลักษณะ และเพิกถอนสิทธิ์ด้วยตนเอง โดยไม่ต้องมีศูนย์กลางที่เชื่อถือได้
เพียงจุดเดียวหลังจากตั้งค่าระบบแล้ว


----------------------------------------------------------------
5. Authorization Index Manager (AIM)
   ตัวจัดการดัชนีสิทธิ์ (AIM)
----------------------------------------------------------------
[EN] An off-chain service that keeps track of authorization indexes,
policy mappings, version numbers, and revocation info. Before any
search runs, the AIM filters out ciphertext indexes the user is NOT
authorized to see — reducing wasted search work and limiting what
metadata gets exposed.

[TH] บริการนอกบล็อกเชนที่คอยติดตามดัชนีสิทธิ์ การจับคู่นโยบาย เลข
เวอร์ชัน และข้อมูลการเพิกถอนสิทธิ์ ก่อนที่การค้นหาใดๆ จะเริ่มทำงาน AIM
จะกรองดัชนีข้อมูลเข้ารหัสที่ผู้ใช้ "ไม่มีสิทธิ์" เข้าถึงออกไปก่อน ช่วยลด
การค้นหาที่สูญเปล่าและจำกัดข้อมูลเมทาดาทาที่อาจรั่วไหล


----------------------------------------------------------------
6. Load Balancing Controller (LBC)
   ตัวควบคุมการปรับสมดุลโหลด (LBC)
----------------------------------------------------------------
[EN] Dynamically spreads encrypted search requests across the
distributed Fog Search Nodes, based on workload, resource
availability, authorization locality, index freshness, and network
conditions. This improves scalability and prevents any one node from
becoming a bottleneck during traffic bursts.

[TH] กระจายคำขอค้นหาที่เข้ารหัสไปยังโหนดค้นหาฟ็อกต่างๆ แบบไดนามิก
โดยพิจารณาจากภาระงาน ทรัพยากรที่มี ความใกล้เคียงของสิทธิ์การเข้าถึง
ความสดใหม่ของดัชนี และสภาพเครือข่าย ช่วยเพิ่มความสามารถในการขยาย
ระบบและป้องกันไม่ให้โหนดใดโหนดหนึ่งกลายเป็นคอขวดเมื่อมีปริมาณคำขอ
เพิ่มขึ้นอย่างรวดเร็ว


----------------------------------------------------------------
7. Fog Search Nodes (FSNs)
   โหนดค้นหาฟ็อก (FSN)
----------------------------------------------------------------
[EN] Distributed edge servers that hold shards (pieces) of the
searchable index and actually run the encrypted keyword search. They
perform authorization-aware search, generate proofs that the results
are correct, and return candidate ciphertexts to authorized users.

[TH] เซิร์ฟเวอร์ที่ขอบเครือข่ายซึ่งกระจายอยู่หลายจุด แต่ละจุดถือดัชนี
ค้นหาเพียงบางส่วน (shard) และเป็นผู้รันการค้นหาคำค้นที่เข้ารหัสจริง
โหนดเหล่านี้ค้นหาโดยคำนึงถึงสิทธิ์การเข้าถึง สร้างหลักฐานยืนยันว่าผล
การค้นหาถูกต้อง และส่งข้อมูลเข้ารหัสที่ตรงกับคำค้นให้ผู้ใช้ที่มีสิทธิ์


----------------------------------------------------------------
8. InterPlanetary File System (IPFS)
   ระบบไฟล์ระหว่างดาวเคราะห์ (IPFS)
----------------------------------------------------------------
[EN] The decentralized storage layer that actually holds the
encrypted medical records. Each file is stored using a content
identifier (CID), giving content-addressable storage, integrity
checking, and deduplication — while keeping the large encrypted
payloads off the blockchain.

[TH] ชั้นการจัดเก็บข้อมูลแบบกระจายศูนย์ที่เก็บระเบียนการแพทย์ที่เข้ารหัส
ไว้จริง แต่ละไฟล์ถูกจัดเก็บโดยใช้ตัวระบุเนื้อหา (CID: Content
Identifier) ทำให้สามารถอ้างอิงตามเนื้อหา ตรวจสอบความถูกต้อง และ
ตัดข้อมูลซ้ำซ้อนได้ ในขณะที่ข้อมูลเข้ารหัสขนาดใหญ่จะไม่ถูกเก็บบน
บล็อกเชนโดยตรง


----------------------------------------------------------------
9. Consortium Blockchain
   คอนซอร์เชียมบล็อกเชน
----------------------------------------------------------------
[EN] Acts as the trusted audit and coordination layer. Instead of
storing encrypted medical data, it stores only compact metadata:
ciphertext commitments, Merkle roots, version-change commitments,
public parameters of the Attribute Authorities, revocation records,
and audit logs. This gives immutable history, verifiable integrity,
and synchronized authorization — with minimal on-chain storage.

[TH] ทำหน้าที่เป็นชั้นตรวจสอบและประสานงานที่เชื่อถือได้ แทนที่จะเก็บ
ข้อมูลการแพทย์ที่เข้ารหัสไว้เอง บล็อกเชนจะเก็บเพียงเมทาดาทาขนาดเล็ก
เท่านั้น ได้แก่ คำมั่นของข้อมูลเข้ารหัส (ciphertext commitment), ราก
Merkle, คำมั่นของการเปลี่ยนเวอร์ชัน, พารามิเตอร์สาธารณะของผู้มีอำนาจ
ด้านคุณลักษณะ, บันทึกการเพิกถอนสิทธิ์ และบันทึกตรวจสอบ (audit log)
ทำให้ได้ประวัติที่แก้ไขไม่ได้ ความถูกต้องที่ตรวจสอบได้ และสิทธิ์การเข้าถึง
ที่ซิงก์กันอยู่เสมอ โดยใช้พื้นที่จัดเก็บบนบล็อกเชนน้อยที่สุด



================================================================
 PART 2 — THE 8 PROTOCOL PHASES
 ส่วนที่ 2 — 8 ขั้นตอนของโพรโทคอล
================================================================

[EN] The full protocol that runs the system is organized into 8
phases, from setting up the cryptography, to a user finally
decrypting a verified search result.

[TH] โพรโทคอลทั้งหมดที่ขับเคลื่อนระบบนี้แบ่งออกเป็น 8 ขั้นตอน ตั้งแต่
การตั้งค่าระบบรหัสลับ ไปจนถึงผู้ใช้ถอดรหัสผลการค้นหาที่ผ่านการตรวจสอบ
แล้วในที่สุด


----------------------------------------------------------------
PHASE I — System Initialization
เฟส I — การเริ่มต้นระบบ
----------------------------------------------------------------
[EN] A trusted initializer sets up the shared cryptographic building
blocks: bilinear groups for attribute-based encryption, a hash
function, AES-256-GCM for encrypting data, HKDF for deriving keys,
and ML-KEM for post-quantum key exchange. Each Attribute Authority
then independently generates its own key pair. Finally, the Fog
Search Nodes, the Load Balancing Controller, the Authorization Index
Manager, and the blockchain metadata store are all brought online.

[TH] ผู้เริ่มต้นระบบที่เชื่อถือได้จะตั้งค่าส่วนประกอบทางรหัสลับที่ใช้ร่วมกัน
ได้แก่ bilinear groups สำหรับการเข้ารหัสตามคุณลักษณะ ฟังก์ชันแฮช
AES-256-GCM สำหรับเข้ารหัสข้อมูล HKDF สำหรับสร้างกุญแจ และ ML-KEM
สำหรับการแลกเปลี่ยนกุญแจแบบต้านควอนตัม จากนั้นผู้มีอำนาจด้าน
คุณลักษณะแต่ละรายจะสร้างคู่กุญแจของตนเองอย่างอิสระ สุดท้าย โหนดค้นหา
ฟ็อก ตัวควบคุมการปรับสมดุลโหลด ตัวจัดการดัชนีสิทธิ์ และที่เก็บเมทาดาทา
บนบล็อกเชน จะถูกเปิดใช้งานทั้งหมด


----------------------------------------------------------------
PHASE II — Multi-Authority Registration and Authorization-State
            Commitment
เฟส II — การลงทะเบียนหลายผู้มีอำนาจ และการสร้างคำมั่นสถานะสิทธิ์
----------------------------------------------------------------
[EN] Each Attribute Authority registers its identity, domain, and
public key on the blockchain. It then initializes the set of
attributes it manages, and computes a compact "authorization-state
commitment" — a single cryptographic fingerprint that binds its
identity, its managed attributes, its current version number, and
its revocation list together. Later, when something changes, only
that authority needs to update this commitment — no global rebuild
is needed.

[TH] ผู้มีอำนาจด้านคุณลักษณะแต่ละรายจะลงทะเบียนตัวตน โดเมน และ
กุญแจสาธารณะของตนบนบล็อกเชน จากนั้นเริ่มต้นชุดคุณลักษณะที่ตนดูแล
และคำนวณ "คำมั่นสถานะสิทธิ์" (authorization-state commitment) แบบ
กระชับ ซึ่งเป็นลายนิ้วมือทางรหัสลับเพียงชิ้นเดียวที่ผูกตัวตน คุณลักษณะที่
ดูแล เลขเวอร์ชันปัจจุบัน และรายการเพิกถอนสิทธิ์เข้าไว้ด้วยกัน ต่อมาเมื่อมี
การเปลี่ยนแปลงใดๆ เกิดขึ้น จะมีเพียงผู้มีอำนาจรายนั้นเท่านั้นที่ต้องอัปเดต
คำมั่นนี้ โดยไม่ต้องสร้างระบบทั้งหมดขึ้นใหม่


----------------------------------------------------------------
PHASE III — User Registration and Version-Bound Authorization
             Profile (VAP) Generation
เฟส III — การลงทะเบียนผู้ใช้ และการสร้างโปรไฟล์สิทธิ์ที่ผูกเวอร์ชัน (VAP)
----------------------------------------------------------------
[EN] Each Data Owner and Data User enrolls with one or more Attribute
Authorities. The authorities verify credentials and issue
attribute-based secret keys. To protect these keys in transit, each
key is encrypted using a post-quantum shared secret (via ML-KEM +
HKDF + AES-256-GCM). Once keys are delivered, the Authorization Index
Manager combines all of a user's attributes and authority commitments
into a single Version-Bound Authorization Profile (VAP) — essentially
a versioned, verifiable summary of everything that user is currently
allowed to do. This VAP will be used later for generating search
tokens and verifying results.

[TH] เจ้าของข้อมูลและผู้ใช้ข้อมูลแต่ละรายจะลงทะเบียนกับผู้มีอำนาจด้าน
คุณลักษณะหนึ่งรายหรือมากกว่า ผู้มีอำนาจจะตรวจสอบเอกสารรับรองและออก
กุญแจลับตามคุณลักษณะให้ เพื่อปกป้องกุญแจเหล่านี้ระหว่างการส่ง กุญแจ
แต่ละดอกจะถูกเข้ารหัสด้วยความลับร่วมแบบต้านควอนตัม (ผ่าน ML-KEM +
HKDF + AES-256-GCM) เมื่อส่งกุญแจสำเร็จแล้ว ตัวจัดการดัชนีสิทธิ์ (AIM)
จะรวมคุณลักษณะทั้งหมดของผู้ใช้และคำมั่นของผู้มีอำนาจต่างๆ เข้าเป็น
"โปรไฟล์สิทธิ์ที่ผูกเวอร์ชัน" (VAP) เพียงชุดเดียว ซึ่งเปรียบเสมือนสรุปสิทธิ์
ทั้งหมดที่ผู้ใช้รายนั้นมีอยู่ในปัจจุบันแบบมีเวอร์ชันและตรวจสอบได้ VAP นี้
จะถูกนำไปใช้ในภายหลังสำหรับการสร้างโทเคนค้นหาและการตรวจสอบผล
การค้นหา


----------------------------------------------------------------
PHASE IV — Policy-Bound Dynamic Search Index Construction
เฟส IV — การสร้างดัชนีค้นหาแบบพลวัตที่ผูกกับนโยบาย
----------------------------------------------------------------
[EN] For each medical record, the Data Owner extracts keywords and
metadata (policy ID, authorization version, domain, timestamp). Each
keyword is hashed together with the policy ID, authorization version,
and domain, producing a token that only makes sense under the CURRENT
policy — it becomes useless if the policy changes later, which
prevents old tokens from being reused or linked across updates. All
these index entries for one record are then batched into a Merkle
tree, and only the resulting Merkle root is committed to the
blockchain (the full tree stays off-chain for efficiency). Finally, a
policy commitment ties the Merkle root, the policy ID, the
authorization version, and the Data Owner's own VAP into one
immutable digest.

[TH] สำหรับระเบียนข้อมูลการแพทย์แต่ละรายการ เจ้าของข้อมูลจะดึงคำค้นหา
และเมทาดาทาออกมา (รหัสนโยบาย เวอร์ชันสิทธิ์ โดเมน และเวลาบันทึก)
คำค้นหาแต่ละคำจะถูกแฮชร่วมกับรหัสนโยบาย เวอร์ชันสิทธิ์ และโดเมน ทำให้
ได้โทเคนที่มีความหมายเฉพาะภายใต้นโยบาย "ปัจจุบัน" เท่านั้น — หากนโยบาย
เปลี่ยนไปในภายหลัง โทเคนเดิมจะใช้การไม่ได้อีกต่อไป ซึ่งช่วยป้องกันไม่ให้
โทเคนเก่าถูกนำกลับมาใช้ซ้ำหรือเชื่อมโยงข้ามการอัปเดตได้ รายการดัชนี
ทั้งหมดของระเบียนหนึ่งรายการจะถูกรวมเป็น Merkle tree และมีเพียงราก
Merkle เท่านั้นที่จะถูกบันทึกลงบล็อกเชน (ต้นไม้ทั้งต้นจะเก็บไว้นอก
บล็อกเชนเพื่อความมีประสิทธิภาพ) สุดท้าย คำมั่นตามนโยบายจะผูกราก
Merkle รหัสนโยบาย เวอร์ชันสิทธิ์ และ VAP ของเจ้าของข้อมูลเข้าเป็นข้อมูล
ที่เปลี่ยนแปลงไม่ได้เพียงชุดเดียว


----------------------------------------------------------------
PHASE V — Secure Data Outsourcing
เฟส V — การฝากข้อมูลอย่างปลอดภัย
----------------------------------------------------------------
[EN] The encrypted record, its search index, and its commitment are
uploaded to IPFS, which returns a content identifier (CID). Instead
of putting the encrypted data on the blockchain, only compact
metadata (CID, policy ID, version, Merkle root, commitment) is
registered on-chain — so blockchain storage cost stays independent of
how much medical data actually exists. After blockchain confirmation,
the searchable index and metadata are synchronized out to the
Authorization Index Manager and the Fog Search Nodes, so future
searches can find the right index shard without scanning the whole
encrypted repository.

[TH] ระเบียนข้อมูลที่เข้ารหัส ดัชนีค้นหา และคำมั่นของระเบียนนั้น จะถูก
อัปโหลดไปยัง IPFS ซึ่งจะคืนค่าตัวระบุเนื้อหา (CID) กลับมา แทนที่จะนำ
ข้อมูลเข้ารหัสไปเก็บบนบล็อกเชนโดยตรง จะมีเพียงเมทาดาทาขนาดกระชับ
เท่านั้นที่ลงทะเบียนบนบล็อกเชน (CID, รหัสนโยบาย, เวอร์ชัน, ราก Merkle,
คำมั่น) ทำให้ต้นทุนการจัดเก็บบนบล็อกเชนไม่ขึ้นกับปริมาณข้อมูลการแพทย์
ที่มีอยู่จริง หลังจากบล็อกเชนยืนยันแล้ว ดัชนีค้นหาและเมทาดาทาจะถูก
ซิงก์ไปยังตัวจัดการดัชนีสิทธิ์และโหนดค้นหาฟ็อก เพื่อให้การค้นหาในอนาคต
สามารถหาดัชนีส่วนที่ถูกต้องได้โดยไม่ต้องสแกนคลังข้อมูลเข้ารหัสทั้งหมด

PHASE VI — Adaptive Authorization-Aware Search Scheduling
เฟส VI — การจัดตารางค้นหาแบบปรับตัวตามสิทธิ์การเข้าถึง
----------------------------------------------------------------
[EN] When a Data User wants to search, they generate a search token
from their keywords plus their VAP (authorization root, version, and
nonce), and send it to the Authorization Index Manager. The AIM
verifies the user's authorization is still valid and current; if not,
the request is rejected immediately without touching the encrypted
index. If valid, the request is passed to the Adaptive
Authorization-Aware Search Scheduler (AASS). For every candidate Fog
Search Node, AASS predicts the total cryptographic cost of running
the search there — combining authorization-check cost, index
traversal cost, proof-generation cost, how out-of-date that node's
authorization sync is, and its current queue wait time — and sends
the query to whichever node has the lowest predicted cost. That node
then searches ONLY the index shards it's authorized to touch, and
returns matching records together with a verification bundle (Merkle
root, policy commitment, and Merkle proof) for each result.

[TH] เมื่อผู้ใช้ข้อมูลต้องการค้นหา จะสร้างโทเคนค้นหาจากคำค้นหาของตน
ร่วมกับ VAP ของตน (รากสิทธิ์ เวอร์ชัน และค่าเลขสุ่มใช้ครั้งเดียว) แล้วส่งไป
ยังตัวจัดการดัชนีสิทธิ์ (AIM) AIM จะตรวจสอบว่าสิทธิ์ของผู้ใช้ยังใช้งานได้
และเป็นปัจจุบันหรือไม่ หากไม่ใช่ คำขอจะถูกปฏิเสธทันทีโดยไม่แตะดัชนี
ข้อมูลเข้ารหัสเลย หากถูกต้อง คำขอจะถูกส่งต่อไปยังตัวจัดตารางค้นหาแบบ
ปรับตัวตามสิทธิ์ (AASS) สำหรับโหนดค้นหาฟ็อกที่เป็นตัวเลือกแต่ละโหนด
AASS จะทำนายต้นทุนเชิงรหัสลับทั้งหมดของการรันการค้นหาที่นั่น โดยรวม
ต้นทุนการตรวจสิทธิ์ ต้นทุนการไล่ดัชนี ต้นทุนการสร้างหลักฐาน ความล้าหลัง
ของการซิงก์สิทธิ์ในโหนดนั้น และเวลารอคิวปัจจุบัน แล้วส่งคำค้นหาไปยัง
โหนดที่มีต้นทุนคาดการณ์ต่ำที่สุด โหนดนั้นจะค้นหาเฉพาะส่วนของดัชนีที่ตน
มีสิทธิ์เข้าถึงเท่านั้น และส่งคืนระเบียนที่ตรงกัน พร้อมชุดหลักฐานยืนยัน
(ราก Merkle, คำมั่นตามนโยบาย และหลักฐาน Merkle) สำหรับผลลัพธ์แต่ละ
รายการ

PHASE VII — Dynamic Index Evolution and Incremental Authorization
              Synchronization
เฟส VII — วิวัฒนาการดัชนีแบบพลวัต และการซิงก์สิทธิ์แบบเพิ่มทีละส่วน
----------------------------------------------------------------
[EN] When a record needs to be inserted, modified, deleted, or a
user's access revoked, the system does NOT rebuild the whole index or
resync every Fog node. Instead, only the affected keyword/index
entries are recomputed, only the responsible Attribute Authority
bumps its version number and recomputes its own commitment, and only
the changed Merkle leaves/paths are updated (not the whole tree). The
Authorization Index Manager then packages this small "diff" — called
an Incremental Authorization Synchronization (IAS) message — and
sends it only to the Fog Search Nodes that actually hold the affected
shard. Nodes that haven't applied the latest update yet are
automatically treated as "costlier" by the scheduler in Phase VI,
so the system naturally avoids routing searches to stale nodes.
Finally, a compact record of the update is anchored on the
blockchain.

[TH] เมื่อต้องเพิ่ม แก้ไข หรือลบระเบียนข้อมูล หรือเพิกถอนสิทธิ์ของผู้ใช้
ระบบจะไม่สร้างดัชนีทั้งหมดขึ้นใหม่หรือซิงก์โหนดฟ็อกทุกโหนดใหม่ทั้งหมด
แต่จะคำนวณใหม่เฉพาะรายการคำค้นหา/ดัชนีที่ได้รับผลกระทบเท่านั้น มีเพียง
ผู้มีอำนาจด้านคุณลักษณะที่รับผิดชอบเท่านั้นที่จะเพิ่มเลขเวอร์ชันและคำนวณ
คำมั่นของตนใหม่ และมีเพียงใบไม้/เส้นทางของ Merkle ที่เปลี่ยนแปลงเท่านั้น
ที่จะถูกอัปเดต (ไม่ใช่ทั้งต้นไม้) จากนั้นตัวจัดการดัชนีสิทธิ์ (AIM) จะรวม
"ส่วนต่าง" ขนาดเล็กนี้เป็นข้อความที่เรียกว่า การซิงก์สิทธิ์แบบเพิ่มทีละส่วน
(IAS) แล้วส่งไปยังเฉพาะโหนดค้นหาฟ็อกที่ถือส่วนดัชนีที่ได้รับผลกระทบ
เท่านั้น โหนดที่ยังไม่ได้รับการอัปเดตล่าสุดจะถูกตัวจัดตารางในเฟส VI
พิจารณาว่ามี "ต้นทุนสูงกว่า" โดยอัตโนมัติ ทำให้ระบบหลีกเลี่ยงการส่ง
คำค้นหาไปยังโหนดที่ข้อมูลล้าสมัยได้เองตามธรรมชาติ สุดท้าย บันทึกการ
อัปเดตแบบกระชับจะถูกบันทึกยึดไว้บนบล็อกเชน

PHASE VIII — Verifiable Retrieval and Secure Decryption
เฟส VIII — การดึงข้อมูลที่ตรวจสอบได้ และการถอดรหัสอย่างปลอดภัย
----------------------------------------------------------------
[EN] Before trusting any search result, the Data User performs four
checks: (1) verify the Merkle proof for each returned ciphertext; (2)
confirm the result's authorization version matches their own current
VAP, and recompute the policy commitment to make sure it matches
exactly; (3) cross-check the result against the immutable metadata
stored on the blockchain, to make sure nothing was altered after
publication; (4) only if all checks pass, fetch the actual ciphertext
from IPFS. Decryption then happens in two steps — first the session
key is recovered using the user's attribute secret key (only works if
their attributes satisfy the record's access policy), then the actual
medical record is decrypted with AES-256-GCM. If any policy or
authenticity check fails, decryption stops immediately and nothing is
revealed. Finally, every retrieval attempt — successful or rejected —
is logged immutably on the blockchain for audit and compliance
purposes.

[TH] ก่อนที่จะเชื่อถือผลการค้นหาใดๆ ผู้ใช้ข้อมูลจะทำการตรวจสอบ 4
ขั้นตอน ได้แก่ (1) ตรวจสอบหลักฐาน Merkle ของข้อมูลเข้ารหัสแต่ละรายการ
ที่ได้รับกลับมา (2) ยืนยันว่าเวอร์ชันสิทธิ์ของผลลัพธ์ตรงกับ VAP ปัจจุบัน
ของตนเอง และคำนวณคำมั่นตามนโยบายใหม่เพื่อตรวจว่าตรงกันทุกประการ
(3) ตรวจสอบไขว้ผลลัพธ์กับเมทาดาทาที่เปลี่ยนแปลงไม่ได้ซึ่งบันทึกไว้บน
บล็อกเชน เพื่อให้แน่ใจว่าไม่มีการแก้ไขใดๆ เกิดขึ้นหลังการเผยแพร่ (4) เมื่อ

นโยบายการเข้าถึงของระเบียนนั้น) จากนั้นจึงถอดรหัสระเบียนการแพทย์จริง
ด้วย AES-256-GCM หากการตรวจสอบนโยบายหรือความถูกต้องขั้นใดขั้นหนึ่ง
ล้มเหลว การถอดรหัสจะหยุดทันทีโดยไม่มีการเปิดเผยข้อมูลใดๆ สุดท้าย ทุก
ความพยายามในการดึงข้อมูล ไม่ว่าจะสำเร็จหรือถูกปฏิเสธ จะถูกบันทึกไว้
