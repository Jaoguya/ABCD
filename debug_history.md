### Ref[52] SamplePre perturbation mode is an approximation
- **Date:** 2026-08-03
- **Status:** *not fixed* — needs user sign-off before any reportable Ref[52] run
- **Why it changed:** `Common/crypto/lattice.py` implements the MP12 gadget-trapdoor toolkit. The cryptographically exact MP12 preimage sampler requires a Cholesky factor of an `m x m` covariance matrix. At Ref[52]'s published `m = 13,812` that is ~1.5 GB in float64 with O(m^3) work per parameter set, which is not tractable in Python.
- **How it will improve:** `PerturbationMode.SPHERICAL` (the default) returns correct, short preimages satisfying `A e = u (mod q)` and pays the dominant cost — the `R @ z` product, ~47.7M multiply-adds. It is therefore a **lower bound** on the exact sampler's latency, not a substitute for it. `PerturbationMode.EXACT` raises `NotImplementedError` with the reason rather than silently degrading.
- **What changed:** Added `PerturbationMode` enum with `NONE` / `SPHERICAL` / `EXACT`; documented the caveat at module level in `lattice.py`. Any Exp. 1/2/5/6 figure for Ref[52] must state which mode produced it.

### MP12 chosen as the TrapGen instantiation for Ref[52]
- **Date:** 2026-08-03
- **Status:** *fixed* — resolved from the published parameters, no guess required
- **Why it changed:** Ref[52] states the `TrapGen(n, m, q, sigma)` interface (Ref[52].txt:104-117) but not its internals, so the instantiation had to be determined rather than assumed.
- **How it will improve:** The published `m` settles it. With `k = log2(q) = 24` the gadget block is `n*k = 6,816`, leaving `m - n*k = 13,812 - 6,816 = 6,996` for the uniform block — just above the `n*log(q) = 6,816` lower bound MP12 requires. That is the MP12 decomposition exactly; a classic Ajtai/GPV TrapGen would not yield `m = 13,812` for `n = 284`. MP12 is thus the algorithm the published parameters describe, not a substitution for it.
- **What changed:** Documented the argument at the top of `lattice.py` and in `crypto.yaml` under `zhuang_lattice_mabse.lattice`.

### HKDF output limit exceeded by PuncturedKey serialization in Guo forward index
- **Date:** 2026-08-05

### Per-candidate LSSS solve charged Ref[41] for work its paper never claims
- **Date:** 2026-08-06
- **Status:** *fixed*
- **Why it changed:** `search()` recomputed the satisfied-row set and the LSSS reconstruction coefficients for every index entry. Both are functions of the access structure and the trapdoor only — no ciphertext component enters either — so a scan of N candidates under one policy ran N identical Gaussian eliminations. Ref[41]'s cost model (Table III, Ref[41].md:485) has no linear-algebra term at all, so this inflated the baseline with overhead the paper does not claim. AGENT_RULES forbids weakening a baseline below its published construction just as firmly as strengthening it.
- **How it will improve:** Search splits into `prepare_query()` (satisfied rows, coefficients, labels — once per trapdoor, still inside the query timer because it is real server work) and `search_with_plan()` (2u+1 pairings per candidate, which is what the paper actually specifies). Reconstruction coefficients are coerced to backend exponent elements once rather than per candidate. `AccessStructure` precomputes its row labels, removing ~2x10^7 f-string allocations per scan at N=10^6. Numerically the pairings still dominate — the solve was on the order of 0.1% of scan time — so this changes fidelity far more than wall clock.
- **What changed:** `scheme.py` — added `QueryPlan`, `prepare_query()`, `search_with_plan()`; `search()` retained as a single-candidate wrapper. `lsss.py` — `AccessStructure.labels` built in `__post_init__`. `experiments.py` — Exp. 2 and Exp. 3 build one plan per trapdoor and reuse it across the scan.

### Pairing-level optimizations deliberately NOT applied to Ref[41]
- **Date:** 2026-08-06
- **Status:** *fixed* — decision recorded; revisit only if the proposed scheme adopts either
- **Why it changed:** Two standard implementation optimizations would materially cut Ref[41]'s measured search cost. Batching the `2u` pairings into a multi-Miller product with one shared final exponentiation typically saves 30-50%. Fixed-base windowed exponentiation would speed up trapdoor generation, since `i^gamma` and `i^xi` are fixed bases reused across every exponentiation in keygen and trapdoor.
- **How it will improve:** Neither is applied. Ref[41]'s competitive claim rests on counted pairing and exponentiation operations, so either optimization would report the baseline as faster than its own published analysis — the mirror image of the defect above, and equally a fidelity break. The constraint that actually binds is parity: if the PROPOSED scheme ever uses batched pairings or fixed-base exponentiation, Ref[41] must get them too or the comparison is confounded. Recorded here so that decision is made once, deliberately, rather than drifting in by whichever library happens to expose it.
- **What changed:** `scheme.py` — `search_with_plan()` documents why the pairings are computed one at a time. No code change; this entry is the record.

### Ref[41] Exp. 2 has a memory ceiling as well as a time ceiling
- **Date:** 2026-08-06
- **Status:** *not fixed* — needs a decision alongside the Exp. 2 time budget
- **Why it changed:** `build_index()` materialises N `KeywordIndex` objects, each holding 2u G1 elements plus a GT and a G1 element — ~22 group elements at u=10. Charm element objects carry substantial Python overhead beyond the 64-byte SS512 encoding, so N=10^6 is on the order of 3 GB before list and object overhead, on a 16 GB instance that must also hold the interpreter and the corpus. Exp. 3 at d=10 builds d shards and is worse in aggregate.
- **How it will improve:** No optimization fixes this without changing what is measured — the ciphertexts must be independent, so they cannot be shared or regenerated lazily inside the timer. It is a second, independent reason the N=10^6 point may not be reachable, and it should be weighed together with the ~55-day time estimate when the team decides whether to cap Ref[41]'s Exp. 2 sweep.
- **What changed:** Nothing yet. Recorded so the memory ceiling is not discovered on the experiment host after a multi-hour index build.
