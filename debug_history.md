### Ref[52] SamplePre perturbation mode is an approximation
- **Date:** 2026-08-03
- **Status:** *not fixed* — needs user sign-off before any reportable Ref[52] run
- **Why it changed:** `Common/crypto/lattice.py` implements the MP12 gadget-trapdoor toolkit. The cryptographically exact MP12 preimage sampler requires a Cholesky factor of an `m x m` covariance matrix. At Ref[52]'s published `m = 13,812` that is ~1.5 GB in float64 with O(m^3) work per parameter set, which is not tractable in Python.
- **How it will improve:** `PerturbationMode.SPHERICAL` (the default) returns correct, short preimages satisfying `A e = u (mod q)` and pays the dominant cost — the `R @ z` product, ~47.7M multiply-adds. It is therefore a **lower bound** on the exact sampler's latency, not a substitute for it. `PerturbationMode.EXACT` raises `NotImplementedError` with the reason rather than silently degrading.
- **What changed:** Added `PerturbationMode` enum with `NONE` / `SPHERICAL` / `EXACT`; documented the caveat at module level in `lattice.py`. Any Exp. 1/2/5/6 figure for Ref[52] must state which mode produced it.

### MP12 chosen as the TrapGen instantiation for Ref[52]
- **Date:** 2026-08-03
- **Status:** *fixed* — resolved from the published parameters, no guess required
- **Why it changed:** Ref[52] states the `TrapGen(n, m, q, sigma)` interface (Ref[52].txt:104-117) but not its internals, so the instantiation had to be determined rather than assumed.
- **How it will improve:** The published `m` settles it. With `k = log2(q) = 24` the gadget block is `n*k = 6,816`, leaving `m - n*k = 13,812 - 6,816 = 6,996` for the uniform block — just above the `n*log(q) = 6,816` lower bound MP12 requires. That is the MP12 decomposition exactly; a classic Ajtai/GPV TrapGen would not yield `m = 13,812` for `n = 284`. MP12 is thus the algorithm the published parameters describe, not a substitution for it.
- **What changed:** Documented the argument at the top of `lattice.py` and in `crypto.yaml` under `zhuang_lattice_mabse.lattice`.

### HKDF output limit exceeded by PuncturedKey serialization in Guo forward index

### Per-candidate LSSS solve charged Ref[41] for work its paper never claims
- **Date:** 2026-08-06
- **Status:** *fixed*

### Pairing-level optimizations deliberately NOT applied to Ref[41]
- **Date:** 2026-08-06
- **Status:** *fixed* — decision recorded; revisit only if the proposed scheme adopts either
- **Why it changed:** Two standard implementation optimizations would materially cut Ref[41]'s measured search cost. The test that pinned the old lazy-rebuild strategy was replaced by one asserting δ revocations rewrite δ paths, plus a timed test that the second 2,000 revocations do not cost more than the first.
  - **`perera_lv_pqabse` (Ref[54]) implemented.** It was in `global.yaml`'s Exp. 1/2/3 sweeps with no code at all. All five phases, 18 passing tests. Its three recorded "decisions needed" are now decided in `crypto.yaml` with reasons — `n=768` (Kyber768's *effective LWE dimension*, not its ring degree 256, which would name the right number for the wrong parameter), `q=2²²` (Kyber's 3329 cannot be reused in a trapdoor construction; 2²² is the largest exponent keeping `lattice.py`'s int64 guard), `|U|=10` (matches thingom), native-mode Exp. 3. **`abe_on_measured_path: false`** is the one boundary worth reviewing: Exp. 1 times PRF+signature, Exp. 2 times the fog index, Exp. 3 is d× Exp. 2 — none reads `ct_abe`, and generating one per record costs a measured 758 ms (211 h at N=10⁶) while changing no measured number in either direction. `test_scheme.py` still exercises Phases 2→5 *with* `ct_abe`, which is what makes the omission honest.
  - **Verification is now possible without AWS.** `~/.venv-malbpq` on the macOS dev host (python3.12 + requirements + pytest), and a smoke driver that runs every runner of every scheme against a 20,000-record synthetic corpus at 2 runs/1 warmup. `yue_ge` 1–5, `perera` 1–3, `guo_vdsse` 1 and 4 all pass. `thingom_pq_abse` **cannot** be verified here — it needs charm-crypto (Linux-only) and `petrelic` has no macOS/arm64 wheel; it remains verified on the experiment host only.

### Campaign wall-clock 34.9h -> 11.2h: incremental nested builds + a --points sweep splitter
- **Date:** 2026-08-29
- **Status:** *fixed* — 651 passed / 5 skipped; split-then-merge verified against an unsharded reference run
- **Why it changed:** User directive: optimise for wall-clock, cost is not a constraint. `guo_vdsse` was the binding track at 34.9h against a 24h cap.
- **How it will improve:** The campaign fits in a working day instead of a day and a half, with the full published sweeps intact — no capped sweep point, no instance upgrade required, and total compute (and therefore cost, ~$14) unchanged.
- **What changed:**
  - **Exp. 2's sweep points are nested prefixes, and were being rebuilt from scratch.** Every point is `records[:n]`, walked in ascending order by `run_experiment`, so the seven points cost **1,880,000 record-inserts to produce a largest index of 1,000,000**. Growing one index costs exactly 1,000,000 and makes six of the seven points free — a **1.88x** saving on the single largest block of the campaign. Applied to `guo_vdsse` (21.13h -> 11.24h) and `perera_lv_pqabse` (5.37h -> 2.86h). Measured on the dev host, perera Exp. 2 went 196.9s -> 127.5s on a 2-point sweep.
  - **Guarded by equivalence tests, and the first attempt was wrong in an instructive way.** Asserting byte-identical EDBs FAILED, correctly: `update()` draws a fresh `ran_id` per record, so two builds of the same records differ in their ciphertexts by construction. The claim that actually matters is that nothing a MEASUREMENT can see differs, so the tests now assert identical index structure (`Ti`/`Tf` key sets, which are deterministic given the keys), identical **and correct** search results, and that intermediate sweep points match a fresh prefix build. Both paths start from `deepcopy`'d key material so the only variable is the build strategy.
  - **`yue_ge` Exp. 2 deliberately NOT made incremental.** Its index is a list of per-batch structures and forward privacy rests on the per-batch state `st_c` (§V-C). Growing it would either reuse `st_c` for records added later — destroying the security property the scheme exists to provide — or append new batches, making batch count depend on sweep position when search cost scales with batch count. A real fidelity wall, not an oversight. At 4.82h it is not the bottleneck.
  - **`infra/sweep.py` + `--points` on every scheme's CLI.** Selects which sweep values a process runs (`--points 2-5`, `--points 100,1000`), so one experiment can be split across instances. Campaign wall-clock is bounded by the largest INDIVISIBLE unit; without this it is a whole experiment (`ma_lb` Exp. 7-8 at 17.5h, `thingom` Exp. 3 at 12.96h), and with it those become one config (0.875h) and one `d` point (1.44h). A value not in the experiment's sweep is an **error**, not a silent no-op: a typo that quietly ran zero points would leave a hole in the campaign that only surfaced when the figure was drawn.
  - **`infra/merge_points.py` reassembles the shards.** Re-aggregates from `raw_runs.csv` rather than averaging shard `results.csv` files — averaging means is only valid at equal run counts and a CI cannot be recovered from other CIs, and README §9 already makes raw runs the source of truth. It **refuses** to merge shards that disagree on `git_commit`, `dataset_sha256` or `config_hashes` (that would be one figure built from two different systems), and refuses duplicate sweep values across shards (two instances ran the same point; merging would double-count it).
  - **Merged output is byte-compatible with an unsharded run**, verified: same columns, same points, same `n_runs`, same raw row count. Getting there caught a real defect — the aggregate's column NAMES are scheme-specific (`ma_lb` writes `secondary_1_mean`, every other scheme writes the metric's real name like `trapdoors_issued_mean`) and are not recoverable from `raw_runs.csv`, which only has `secondary_metric_N`. The merger now reads the target names from a shard's own `results.csv` and maps positionally, so `Plots/generate_plots.py` reads the merged file unchanged. Without that fix the merged file would have loaded and plotted nothing.
  - **Wall-clock now:** per-scheme (5 instances) **25.0h**; with `--points` splitting **11.2h**, bounded by `guo_vdsse` Exp. 2's single N=10⁶ build, which incremental building makes inherently sequential. Total compute 74.4h either way.
  - **To go below 11.2h** the N=10⁶ build itself must be parallelised. It is untimed setup, so unlike Ref[41]'s search parallelisation it changes no reported number and needs no §V disclosure — but `guo`'s `update()` carries per-keyword counters, so it means sharding by keyword and merging the forward index, i.e. touching a baseline's construction. Not attempted; it needs the same equivalence-test treatment the incremental build got.

### guo_vdsse OOM-killed campaign-wide; GGM domain 128 -> 64, Exp. 2 capped at 2e5
- **Date:** 2026-08-29
- **Status:** *fixed* — parameter changed with provenance; guo re-run pending
- **Why it changed:** The 2026-08-29 campaign ran 9 nodes for 8.7h. Four schemes succeeded (55 of 57 results reportable; the two exceptions are the known Fabric-ledger gap on our Exp. 4/6). **Every guo_vdsse job failed, all with rc=137 — OOM.** Kernel log: `Out of memory: Killed process (python3) anon-rss:15666452kB` on a 16 GiB host.
  - **Root cause:** guo's forward index stores a t-punctured GGM key per document (Alg. 2 lines 18-19), sized O(|W_id| * log|X|). At `domain_bits: 128` and corpus v4's 31.7 keywords/document that is **138.2 KB per document** — 14.15 GB at N = 10^5, which is what Exp. 1, 3 and 5 all index.
  - **Why the pre-run estimate missed it (twice).** First measurement said 38 GB — taken while a concurrent job had the machine at 61 MB free with 25.6 GB in the macOS memory compressor, so RSS was under-reported and the reading drifted. Second said 9.5 GB — that one punctured at `range(t)`, i.e. **adjacent** points, which share tree prefixes and collapse the co-path to ~138 nodes. The real puncture points are `F2(w)` outputs, pseudorandom, sharing nothing: **3,915 nodes**. Same class of error as extrapolating from a dev corpus with the wrong keyword/pair shape — the test used a shape the real system never produces. The TIME model was fine: predicted 40.5 ms/record, measured 42.3.
- **How it will improve:** guo's four experiments become runnable at all, and the parameter now follows the same sizing rule the repo already applies to its other punctured-PRF scheme.
- **What changed:**
  - **`crypto.yaml`: `guo_vdsse.puncturable_prf.domain_bits` 128 -> 64.** **[results-affecting for guo Exp. 2, 4, 5]** Ref[35] never publishes |X| — it defines the t-Pun-PRF abstractly (`Ft: K x X -> Y`, :370-382) and fixes only lambda = 128 and a 192-bit hash output. 128 came from reading "tree depth = |X| in bits" off lambda, which conflates the KEY length with the DOMAIN. The domain need only hold `F2(w)` for 2,023 distinct keywords; 64 bits gives a ~1e-13 collision bound. **The repo's own precedent decides the rule:** yue_ge's MSRE derives its domain from the space it addresses (15 bits for a 19,171-bit Bloom filter) and its docstring rejects "some wider fixed domain ... covering an address space the scheme never touches". guo at 128 was the sole outlier — 8.5x deeper than yue_ge's while addressing a *smaller* space. 64 is still 4x deeper, deliberately conservative.
  - **`exp2_search.py`: sweep capped at 2*10^5** (was 10^6). Measured at 64 bits: N=10^5 -> 5.2 GB, 2*10^5 -> 10.3 GB, 5*10^5 -> 25.9 GB, 10^6 -> 51.7 GB, against a 16 GiB host holding a ~2 GB corpus.
  - **Context that reframes both, from Ref[35] itself:** the paper's own evaluation ran on **112 GB of memory** over a dataset of 517,399 files / 1,989,805 pairs — **3.85 keywords per document**. Corpus v4 averages **31.70**, 8.2x denser, and this index is linear in that. At our density even the paper's own machine could not hold N = 10^6 at 128 bits (141 GB). The cap is a corpus-density and hardware limit, not an implementation defect.
  - **Order of decision, recorded deliberately:** the domain change was justified and taken on the grounds above **before** any cross-scheme comparison was available (guo produced no results). It does make guo faster on Exp. 2/4/5 — Exp. 1 is unaffected, since trapdoor generation never touches the punctured PRF. AGENT_RULES "Bias Detection" requires that a parameter is not chosen for its effect on the ranking; this note exists so that sequence is auditable.
  - **§V must state:** guo's punctured-PRF domain is sized to the keyword universe as Ref[55]'s is, and Exp. 2 is capped at 2*10^5 for memory at corpus v4's document density.
