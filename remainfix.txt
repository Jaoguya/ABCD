DECIDE-2 — What statistic do the baselines get reported with?          [DECIDE]
================================================================================
README §7 mandates "mean ± 95% CI" with outliers kept. For two baselines that
produces numbers that cannot be defended.

  guo Exp. 3 (FRESH 10-rep data, 9 of 9 points distorted):
      d=2   median  36.555   mean 53.786 ± 46.238   max 194.118
      d=6   median  21.302   mean 53.394 ± 46.814   max 193.964
      d=10  median  18.538   mean 42.816 ± 43.343   max 193.356
      -> the CI is ~86% of the mean.
      -> max is pinned at ~194 ms at EVERY d: that is guo's EDBcache miss cost
         (its own Alg. 3 lines 25/28). Cache hits run 18-36 ms.
      -> THE MEAN DELETES THE FINDING. Medians fall cleanly with d
         (36.6, 21.3, 18.5) — that is the scaling Exp. 3 exists to show. The
         means are flat near 50 ms and hide it entirely.

  yue_ge Exp. 2 (FRESH 10-rep, 7 of 7 points distorted):
      mean is 16.9x the median. At N=10^6 the ten runs spanned 0.33-1408.65 ms.
      Peony++ is output-sensitive: O(n_w^l) is literally the matching-file
      count, so every one of those runs is a CORRECT measurement of a different
      keyword.

NEITHER IS A BUG. Re-running reproduces both exactly. This is a reporting
decision, not a defect to fix.

Note the 30 -> 10 repetition change makes this WORSE, not better: fewer samples
from a heavy-tailed distribution make the MEAN less stable.

Options: report median + IQR; report cold and warm separately; or keep the mean
and disclose prominently. All three change published numbers.

BUILD-2 — Exp. 4 aggregate proof ("Tier 2")                             [BUILD]
================================================================================
This is the ONLY change that moves us from 3rd to 2nd.

Where we are, fresh 10-repetition data, all three schemes:

      r        Proposed        Scheme [30]      Scheme [35]
     10    0.172 ± 0.011     0.135 ± 0.005    0.062 ± 0.002
    100    1.505 ± 0.005     0.963 ± 0.027    0.524 ± 0.006
   1000   15.411 ± 0.072     9.139 ± 0.047    5.195 ± 0.015

3rd of 3 at every point. Every interval is under 3% of its mean — this is not
close and it is not noise.

ROOT CAUSE IS THE PROOF SHAPE, not the crypto:

      per returned result:   ours 15.43 us   [30] 9.14 us   [35] 5.20 us
      proof size at r=1000:  ours 181.34 KB  [30] 0.06 KB   [35] 0.03 KB

Our proof grows linearly (1.93 KB at r=10 -> 181.34 KB at r=1000). Both
baselines ship a CONSTANT-size proof at every r. We send ~2,900x more bytes and
then verify all of them. Verification cost tracks what it has to hash.

All three schemes are the same complexity class (linear in r, R^2 >= 0.9998).
The ordering is set entirely by the constant that O-notation discards, which is
exactly why the cost table cannot predict it.

TARGET (measured on a prototype, not projected):
    3.43x -> ~8.2 ms at r=1000, which is under [30]'s 9.14 -> 2nd place
    proof size 86 KB -> 0.34 KB

DESIGN: one response-level tree over the r leaves, one root check, plus the
per-record anchor checks. The client still hashes EVERY returned entry —
nothing is skipped, nothing is sampled.

COSTS / CONSTRAINTS:
  - Changes Phase VIII. The construction section and the security argument move
    with it. This is a paper change, not just a code change.
  - An aggregate check says the batch is bad without saying WHICH result failed.
    Preserve per-result granularity by falling back to per-bundle verification
    ONLY when the aggregate check fails.
  - Already shipped (commit f413e62): Tier 1 amortisation of Steps 2-3 over the
    record, 28.027 -> 15.411 ms (1.82x on the host). It narrowed the gap to [30]
    from 3.09x to 1.69x and was never expected to close it.

OPS-2 — the result-handling procedure destroyed data once and nearly     [OPS]
        did so twice. Fix the watchdog before the next campaign.
================================================================================
INCIDENT 1 (data lost). perera's finished 10-repetition run — Exp. 1-3,
completed 2026-09-02 18:42:40 — was DESTROYED on 2026-09-03 when the assistant
ran `git checkout -- .` on its node to clear the tree for a pull. Results are
TRACKED files; they reverted to the 2026-08-29 30-rep versions. No untracked
survivors, no backup on that box newer than 2026-08-29. Unrecoverable. Re-run.

  RULE: never run `git checkout -- .` on a fleet node. Read `git status` and
        understand every modified path first.

INCIDENT 2 (caught before damage). Each watchdog runs `git add -A Schemes/`,
which is too broad. perera's node commit therefore ALSO carried 39 stale
2026-08-29 ma_lb_pq_vdse result files that were dirty in its working tree.
Merging that bundle would have overwritten the FRESH proposed-scheme results
with month-old data.

  FIX: narrow the watchdog's `git add` to the scheme that node actually ran.
       One line. Do it before the next campaign.
  RULE: never merge a node bundle. Always
            git diff --name-only <ref>~1 <ref>
        then check out only that scheme's paths.

INCIDENT 3 (caught by a test). Importing perera's results with
`git checkout refs/node/perera -- Schemes/perera_lv_pqabse/` took the node's
version of EVERY file under that path — source and docs at the node's old
commit — silently reverting the 30->10 docstring fixes in src/harness.py.
test_repetition_count_agreement.py failed on the next run and named the exact
lines. Without that test it would have shipped.

  RULE: `git checkout <ref> -- <dir>/` is not a data import. Restrict it to the
        result files, or verify what else moved.
