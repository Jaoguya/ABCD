## Role in this project

The attribute-based searchable-encryption baseline, and the only one built on a
**Type-I (symmetric) pairing**. It supplies the pairing-cost comparison point
for trapdoor generation, search and cross-domain scalability.

It has no dynamic-update primitive, no result-verification primitive, no
authorization-synchronization primitive and no scheduler. Excluding it from
Experiments 4–9 is not a convenience — including it would claim capabilities the
paper does not have.

## How the scheme works

```
src/scheme.py       the five phases
src/lsss.py         LSSS access structure
src/experiments.py  experiment bodies, including experiment_2_projected()
```

A **single-authority CP-ABSE over a Type-I (symmetric) pairing**, secure under
DBDH. Five phases: setup, key generation, encryption, search, decryption.

The cost structure is what matters here:

- **Trapdoor generation** is `2u` exponentiations, `u` the attribute count.
- **Search is `2u + 1` pairings *per candidate record*, with no index structure
  and no early termination.** Every record in the collection is paired against.
  This is the published behaviour, and it is the single fact that shapes
  everything below.

The search relation was verified symbolically before implementation, so a
failing search here is a bug in this repository rather than in the paper:

```
e(CS_3j, L_1z) · e(CS_4j, L_0z)
  = e(i,i)^{gamma·delta_j·xi·eta} · e(i^{gamma·delta_j}, O_2)^{-a_z·eta}
```

**Multi-keyword handling.** The paper's scheme is single-keyword. The
benchmark's `q = 5` conjunctive workload is served natively as `q` independent
trapdoors and `q` independent searches with client-side intersection
(`multi_keyword.mode = independent_trapdoors`), recorded in every
`run_meta.json`.

**Decryption is on no measured path.** Experiments 1–3 exercise setup, key
generation, encryption, trapdoor generation and search only. That matters
because the paper's decryption path is not recoverable as written: `K_2`/`K_3`
are printed inconsistently between two sections, `q_UR` in `K'_3` is never
defined, and a free `a` in `K_3` appears nowhere else. Those components are
implemented on the most defensible reading and marked as such, but **no reported
number depends on them.** Everything Experiments 1–3 measure is unambiguous in
the paper and is reproduced exactly.

## Configuration

`crypto.yaml`, `thingom_pq_abse` block.

| Key | Value | Provenance |
|---|---|---|
| `pairing.type` | type-1 | published — symmetric pairing |
| `pairing.backend` | `charm_ss512` | the published SS512 curve |
| `pairing.dev_fallback_backend` | `petrelic_bn254` | Type-III, development only |
| `pairing.allow_dev_fallback_in_reportable_runs` | false | |
| `hash_output_bits` | 256 | |
| `attributes.u` | 10 | **benchmark, not published for this evaluation** |
| `multi_keyword.mode` | `independent_trapdoors` | benchmark |

**`u` is a benchmark decision.** Neither this paper nor the manuscript publishes
an attribute count for this evaluation — the paper fixes `u = 30` only for its
own figure captions. It is held in `crypto.yaml` so the value is hashed into
every `run_meta.json`, because `u` places this baseline on both Experiment 1
(`2u` exponentiations) and Experiment 2 (`2u + 1` pairings per candidate). The
runner **refuses to start** if the key is missing rather than defaulting it.

**A Type-III backend cannot run this scheme at all.** The construction pairs two
elements of the *same* group throughout (`e : I1 × I1 → I2`). On a Type-III
backend the second argument must come from `G2`, so the first pairing in
`setup()` raises from inside the library. The runner fails with that explanation
rather than a library error. `charm-crypto` is Linux-only, so this scheme cannot
be developed on macOS or Windows.

## Scheme-specific flags

Beyond the common contract in [skill.md](skill.md) §7:

| Flag | Default | Effect |
|---|---|---|
| `--dev` | off | permit a development backend and unverified corpus; output is stamped `reportable: false` |
| `--max-seconds-per-run` | 7200.0 | per-point wall-clock budget; a point whose estimate exceeds it is recorded `status=failed` rather than attempted |

Output flag is `--output`; warm-ups are `--warmups`. `--dataset` is accepted.

Fixed in `main.py`: `EXP1_Q_VALUES = 1..20`,
`EXP2_INDEX_SIZES = [10⁴, 5·10⁴, 10⁵, 5·10⁵, 10⁶]`,
`EXP3_DOMAIN_COUNTS = 2..10`, `EXP3_TOTAL_INDEX_SIZE = 2000` held constant
across the `d` sweep.

**Without a verified corpus it refuses to start** unless `--dev` is passed. Its
`results.csv` alone carries a **`measurement_type` column**. Points are flushed
between sweep points with a `PARTIAL` marker; `run_meta.json` appears only on
completion.

`--max-seconds-per-run` was raised from 1800 to 7200 on 2026-08-30. At 1800 the
sweep could not reach the range it is meant to measure: a live run recorded
`N = 50,000` as `budget_exceeded_est2157s_budget1800s` and stopped, so the three
largest points were never attempted. **A timeout decides whether a run finishes,
never what it reports.**

## The Experiment 2 projection

### Why it exists

Search is `O(N)` pairings with no early termination, as published. One run at
`N = 10⁶` costs roughly 11.3 hours and the full sweep far exceeds the per-track
compute budget. The alternative to a labelled derived curve is **no curve at all
above `N = 10⁴`** — and a baseline that stops after one point tells a reader
less than a derived one that is labelled as derived.

The user instruction of 2026-09-03 sets the boundary: **search for real up to
10,000 records, derive the rest.**

### What is *not* claimed

- Scheme 41 was **not executed** at `N = 5·10⁴` or above. Those rows are
  computed, not run.
- The derived values are **not measurements** and carry no confidence interval,
  because a computed point has no variance.
- Nothing is invented, guessed, or taken from the original paper's own reported
  figures. Every derived point is a function of measurements made **in this
  benchmark, on this host, under this configuration**.

### The equation

`experiments.experiment_2_projected()`:

```
cost(N) = intercept + slope · N
```

`slope` and `intercept` come from **ordinary least squares over three measured
anchors**:

```
_PROJECTION_ANCHORS = (1000, 5000, 10000)
```

Each anchor is a real search at `repetitions = 10` with 5 discarded warm-ups,
with the worker count **forced to 1**. Forcing `P = 1` matters: at
`N = 1..1000` there is nothing to parallelise, but the pool still forks, and the
CPU timer sums child resource usage — so fork and teardown would land inside the
measurement and be attributed to the `intercept`, the very term being isolated.
That would inflate the small anchors more than a large `N` and tilt the slope.

The keyword set is drawn **once**, before the anchor loop, and reused at every
anchor, so query selectivity cannot contaminate the slope.

### Why not scale from a single point

A query at `N = 1` costs `fixed + per_candidate`, where `fixed` is `q` trapdoor
generations plus query planning — work done **once per query** whatever `N` is.
Multiplying `cost(1)` by `N` charges that setup `N` times over: at `10⁶`, a
million trapdoor generations for a scan that does `q`. That does not merely add
noise, it **inflates this baseline systematically** — and inflating a baseline
inflates the proposed scheme's apparent advantage. Fitting the slope separates
the per-query fixed cost into the intercept, where it belongs.

**Three anchors, not two.** Two points *fit* a line and cannot *test* one.
Linearity is the load-bearing assumption of the whole projection, so it is
measured and reported as a residual rather than asserted.

### The fitted values in the banked run

`Schemes/thingom_pq_abse/exp2_search_latency/run_meta.json`, campaign run of
2026-09-02 on `m6i.xlarge`, `charm_ss512`, `u = 10`, `q = 5`, corpus `synthea` /
`e56ca2d1…`:

| Anchor `N` | Mean (ms) | CI95 (ms) | n_runs | Pairings |
|---|---|---|---|---|
| 1,000 | 74,083.88 | 210.61 | 10 | 105,000 |
| 5,000 | 370,716.88 | 709.54 | 10 | 525,000 |
| 10,000 | 737,651.13 | 1,506.34 | 10 | 1,050,000 |

| Fit | Value |
|---|---|
| `slope_ms_per_record` | 73.7156442543967 |
| `intercept_ms` | 1000.5290028509335 |
| `model` | `cost(N) = intercept + slope · N` |
| max abs. relative residual | 0.85 % |

Residuals across the three anchors are −0.85 %, +0.31 %, −0.07 % — linearity
holds to under one percent. That is the *evidence* for the projection, not an
assumption behind it.

### What the projection produces

| `N` | `search_cpu_time_ms` | `measurement_type` | `n_runs` | `ci95` |
|---|---|---|---|---|
| 10,000 | 737,651 | **measured** | 10 | 1,506.34 |
| 50,000 | 3,686,780 | projected | 1 | `nan` |
| 100,000 | 7,372,560 | projected | 1 | `nan` |
| 500,000 | 36,858,800 | projected | 1 | `nan` |
| 1,000,000 | 73,716,600 | projected | 1 | `nan` |

`N = 10⁴` is both an anchor and a sweep point. It is emitted with its **actual
runs** rather than a value fitted through itself, so the figure carries a genuine
measurement with a genuine confidence interval at that `N` and the projection
starts strictly above it.

A projected row's `ci95` is `nan` — a computed point has no variance.
`generate_plots.py` renders `nan`, and any single-run point, as **no error bar**
rather than a zero-length one.

Secondaries under projection:

- `pairings_computed` is projected as `pairings_per_record · N`. Exact, not
  fitted: the count is `q · N · (2u + 1)` by construction.
- `wall_clock_ms` is **left blank** — it depends on the worker count and is not
  projectable.

### How it reaches the figure

`generate_plots.py` reads `measurement_type` and draws any `projected` point
with a **hollow marker and no error bar**, visibly bare beside a measured one.
The manuscript's Fig. 2 caption says the same thing in words. Both must stay —
a derived point drawn solid is indistinguishable from a measured one.

### One extrapolation path, deliberately

There was a second, general-purpose one — `infra/extrapolate_points.py`, which
scaled an anchor by `target/anchor` and wrote `n_runs = 0`. It never produced
any banked data and was **deleted on 2026-09-12**: two extrapolation paths, one
unused, is exactly how a derived point ends up attributed to the wrong method.
The fit above is the only way a projected Scheme 41 point is produced.

## Differences from the paper

- **The post-quantum claim is self-refuting in the source paper.** It asserts
  that DBDH "forms the foundation of the post-quantum security claims in this
  work" while, elsewhere in the same paper, stating that pairing-based
  cryptography "is not thought to be feasible in a post-quantum setting since it
  depends on Diffie-Hellman-type problems, which quantum computers can solve
  effectively." The construction is reproduced **exactly as published** and the
  contradiction reported as an observation. Do not "fix" it. The manuscript's
  comparison table accordingly does not credit this scheme with post-quantum
  security.
- **The decryption path is not recoverable as written** — see *How the scheme
  works*. Nothing measured depends on it.
- **The manuscript's Fig. 2 caption understates the method.** It says Scheme 41's
  points above `N = 10⁴` are "extrapolated linearly from its measured `N = 10⁴`
  anchor" — singular. The code fits by least squares over **three** measured
  anchors and reports a linearity residual. The caption is not wrong about
  *what* is derived, but it describes a weaker procedure than the one performed.
  Open, for paper revision. Do not change the code to match the caption.
- **No "reported runtime" from the original paper appears anywhere in this
  benchmark.** Every Scheme 41 number, measured or derived, originates in this
  repository's own measurements. A claim that some figure here comes from the
  source paper's own reported results is not supported by the code or the banked
  data.

## Implementation notes

- **The full `10⁴–10⁶` sweep is deliberate, not opportunistic.** An earlier
  change moved Experiment 2 to a single point at `2·10⁴` because the parallel
  speedup made it affordable. That point aligned with **no other scheme's**
  measurements, leaving Scheme 41 alone on an axis with nothing to compare
  against. Affordability never sets this range; **comparability does**. `N` must
  always be a point `global.yaml`'s `exp2_search_latency.values` sweeps.
- **`n_runs = 1` on a projected row is the honest encoding of "one computed
  value"**, not a claim of one measurement. The anchors behind it ran at
  `n = 10`.
- **Experiment 2's search is parallelised across forked processes; Experiment 3
  is single-threaded on purpose.** Both counts are in `run_meta.json`
  (`exp2_search_processes`, `exp3_search_processes`). Parallelism is a
  hardware-utilisation detail, not an algorithmic change: pairing counts and
  match sets were verified identical against the single-threaded path.
- **Experiment 3 holds the total index size at 2,000 across the `d` sweep**, so
  the per-domain index shrinks as `d` grows. Recorded in `run_meta.json` because
  Experiment 3's variable is `d` and the held size appears in no `results.csv`
  column. The proposed scheme fixes per-domain size while the baselines fix the
  total — opposite sizing rules, and each curve's shape partly reflects its
  own.
- This scheme's Experiment 2 curve has **no confidence intervals** above the
  anchor where every other scheme has them. That is a real cost of the
  projection, disclosed rather than hidden.
